# RAMS JSON API

RAMS exposes a read-only, versioned JSON API for external integrations such as
FAIR Station.

Everything lives under the base path `/api/v1`.

## Authentication

The API uses Bearer tokens issued to an `ApiClient` record — one record per
integrating application.

### How tokens work

- A token is generated by the application when an `ApiClient` is created, and is
  printed exactly once.
- Only a SHA-256 digest of the token is stored (`api_clients.token_digest`). The
  plaintext token is never persisted, so it cannot be recovered later.
- Tokens look like `rams_` followed by a URL-safe random string.
- Send the token as a Bearer token:

  ```
  Authorization: Bearer rams_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
  ```

- A client can be deactivated by setting `active` to `false` on its `ApiClient`
  record. Calls with a deactivated token return `401`.
- Tokens can be rotated with `ApiClient#rotate_token!`, which issues a new token
  and invalidates the previous one.

### Scoping

An `ApiClient` may optionally belong to a `Reserve`. Endpoint controllers decide
how that scope narrows what they return: a client with no reserve is a
platform-wide integration, while a client with a reserve sees only that
reserve's research. A record outside the client's scope is reported as `404`
(not `403`), so the API never confirms the existence of inaccessible records.

## Creating an API client

Use the `api:clients:create` rake task. It prints the token once; store it in
the integrating application's secret store.

```bash
# Platform-wide client (all reserves)
docker compose exec web env NAME="FAIR Station" bin/rails api:clients:create

# Client scoped to one reserve
docker compose exec web env NAME="FAIR Station (Valentine)" RESERVE_ID=3 \
  bin/rails api:clients:create
```

Outside Docker, drop the `docker compose exec web` prefix:

```bash
env NAME="FAIR Station" bin/rails api:clients:create
```

Output:

```
Created API client 1 (FAIR Station)
Token: rams_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

## Response format

Collection responses use a `data` + `meta` envelope:

```json
{
  "data": [ { "id": 42, "title": "...", "...": "..." } ],
  "meta": {
    "page": 1,
    "per_page": 25,
    "total_pages": 4,
    "total_count": 87
  }
}
```

Single-resource responses use `data` only:

```json
{ "data": { "id": 42, "title": "...", "...": "..." } }
```

Endpoint payloads are serialized by presenters that expose an explicit
allowlist of fields; database columns are never exposed by default.

## Errors

Errors are returned as JSON with an `error` key:

| Status | Body | Cause |
| --- | --- | --- |
| `401` | `{ "error": "unauthorized" }` | Missing, malformed, unknown, or deactivated token. |
| `400` | `{ "error": "bad_request", "detail": "..." }` | Invalid query parameter. |
| `404` | `{ "error": "not_found" }` | Unknown record, or a record outside the client's scope. |

A `401` response includes a `WWW-Authenticate: Bearer realm="rams-api"` header.

## Pagination

Collections use offset pagination (`page` / `per_page`, capped at `100`) and are
ordered by `created_at` descending with `id` as a tiebreaker, so page boundaries
are deterministic. Offset pagination can still drift if records are created
while a client is paging; move to keyset pagination keyed on `(created_at, id)`
if that becomes a problem.

## Not yet implemented

- Endpoints. The path version and authentication/response layers are in place;
  resource controllers are added on top of `Api::V1::BaseController`.
- Write endpoints (the API is read-only).
- OAuth2 / Doorkeeper. Authentication is isolated behind
  `Api::BaseController#authenticate_api_client!`, so Doorkeeper can replace the
  token check without changing endpoint controllers.
- Rake tasks for rotating or deactivating clients (the model supports both).
- Rate limiting.
